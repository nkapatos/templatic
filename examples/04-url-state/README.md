# 04 · url state

An inbox whose tab, search and open item live in the URL
(`/?tab=done&q=keys&open=7`). With JavaScript a click or a search swaps
the inbox in place and pushes the new URL; without it the same link or
form is a plain page load. A reload, a deep link or the back button lands on the same state.

```sh
npm install
go tool templatic generate
go run .                     # http://localhost:8080
```

## What it shows

- **The URL is the state.** `View` (`components/inbox.go`) holds the tab,
  the search and the open item. `ParseView` reads it from the query on
  `GET /`, `View.URL` writes it back for every href, and `Clean` puts a
  hand-edited value back in range.
- **A session region per viewer.** `//templatic:region topic-of=InboxTopic`
  above `templ Inbox(v View)` makes `templatic generate` declare
  `InboxRegion` (`components/inbox_tc.go`). The page paints it with
  `InboxRegion.Render(v)`; the command handler pushes a new one with
  `InboxRegion.Swap(s, v)`, to that session only. Compare
  [02-live-value](../02-live-value): a world `live.Cell` is one value every
  page shows; here two windows on different tabs never touch each other.
- **Links that swap or load.** `ui.Link(Navigate, view, view.URL())` renders
  an ordinary `<a href>`. With JS the runtime raises `Navigate` instead,
  which the command declares `.Swaps(InboxTopic)`; a page without that
  region would follow the href.
- **The handler names the new address.** `navigate` (`main.go`) returns
  `live.At(v.URL())`; the runtime pushes that URL with the command as its
  history entry. Back and forward replay the entry's command, so the swap
  comes back without a page load.
- **Search is a plain GET form with a hook.** The form
  (`components/inbox.templ`) sits outside the region, so a swap never
  morphs the field being typed in. Without JS it GETs `/?tab=…&q=…`, the
  same page route. With JS the `search` hook (`client/search.ts`) raises
  `Navigate` instead, on submit and once typing pauses, and sets the
  fields from the URL after every other navigation, back and forward
  included. Each search it raises is a history entry of its own:
  `live.At` always pushes
  ([#61](https://github.com/nkapatos/templatic/issues/61)).
- **Tests through livetest.** `main_test.go` runs `Navigate` on one of two
  sessions and checks the receipt URL and that only that session got a
  swap.

The query is parsed by hand: there is no typed query decoding yet
([#5](https://github.com/nkapatos/templatic/issues/5)).

Going back to the entry the page was first loaded at reloads it: that entry
has no command to replay. Clicking faster than the server answers can leave
the address and the inbox out of step
([#34](https://github.com/nkapatos/templatic/issues/34)).

## Files

| File | Holds |
|---|---|
| `main.go` | the world, the `Navigate` handler, the page route |
| `main_test.go` | the command and URL round-trip tests |
| `components/inbox.go` | the items, `View` and its parsing, `Navigate` |
| `components/inbox.templ` | the page with the search form, the `Inbox` region |
| `components/layout.templ` | the document, `Head`, `Boot` |
| `client/search.ts` | the `search` hook |
| `client/app.ts`, `client/app.css` | the bundle's entry and stylesheet |
| `public/favicon.svg` | a file the app serves itself |

`*_templ.go` and `*_tc.go` files are generated by `templatic generate` and
committed. `.templatic/` is generated and ignored.
